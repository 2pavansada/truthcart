# EVALUATION_PLAN.md — Evaluation, latency and cost measurement

> Design only. The official `evaluate.py`, its scoring formula, the 150 test questions and their hidden expectations have **not been seen** (UNK-10, UNK-11). Nothing below has been run; every number in a template is a blank to be filled by a real run. Any metric that is ours is labelled **PROVISIONAL**.

## 1. Principles

1. **Preserve the official evaluator.** Its interface and scoring semantics are authoritative. Our bridge adapts *to* it; we do not change it, and we report its output verbatim.
2. **No invented official formula.** Our composite score is explicitly labelled provisional and is never presented as the official result.
3. **No hardcoding.** Hidden-test answers are never encoded, and no code path may key on test question text (§8).
4. **Independence.** The auditor that grades final answers is written separately from the runtime validator.
5. **Reproducible.** Every report records commit, config hashes, manifest hash, model IDs, mode, hardware and date.
6. **Distinguish measured from estimated** for tokens, memory and cost.

## 2. Integrating the official evaluator (Day 1 protocol)

Day 1 tasks (owner: member 4; recorded in `docs/OFFICIAL_EVALUATOR_NOTES.md`):

| # | Question | Record |
|---|---|---|
| E1 | How does `evaluate.py` obtain answers? (imports a Python function / calls an HTTP endpoint / launches a subprocess / reads an output file) | Exact name, signature, URL or CLI |
| E2 | Input shape: single string, list of turns, dict with fields? Multi-turn supported? | Example |
| E3 | Output shape expected: plain text, dict (`answer`, `citations`, `decision`, …)? | Example |
| E4 | Citation format it recognises (inline `[P102]`? list of IDs? policy section naming?) | Pattern |
| E5 | Decision labels it expects (e.g. answer/clarify/refuse spelling) | Mapping table for the bridge |
| E6 | Scoring: per-question fields, penalties (price hallucination?), aggregate formula, output files | Verbatim |
| E7 | What are the "hidden expected behaviours" — categories, label vocabulary? Is any label visible in the question file? | Notes |
| E8 | Runtime constraints: time limit per question, offline requirement, working directory, environment | Notes |

**Integration modes** (choose per E1; all share `Orchestrator.handle`):

| Mode | Bridge artefact |
|---|---|
| A. Python callable | `eval/official_bridge.py` exports the exact function the evaluator imports; wraps `Orchestrator.handle`; converts our `ChatResponse` into the required return shape |
| B. HTTP | Same bridge mounted as an extra route (e.g. `POST /official/answer`) **only if** the evaluator's request/response shape differs from `/api/chat` |
| C. CLI/file | `scripts/run_official.py` reads the official question file, calls the bridge, writes the expected output file |

**Bridge contract**
```python
class OfficialBridge:
    def __init__(self, orchestrator: Orchestrator, mapping: OfficialMapping): ...
    def answer(self, question: OfficialQuestion) -> OfficialAnswer: ...   # shapes defined from E2/E3 on Day 1
```
Responsibilities: session handling (fresh session per question unless E2 shows multi-turn grouping), decision-label mapping (E5), citation formatting (E4, via `app.citation_format`), timing capture. **It contains no per-question logic**, no lookup tables keyed on question text, and no reading of expected outputs.

If the evaluator's categories do not match ours, only `OfficialMapping` changes; the core vocabulary (ANSWER/CLARIFY/REFUSE + reasons) stays.

## 3. Test-set adapter

```python
@dataclass(frozen=True)
class EvalCase:
    case_id: str
    turns: list[str]                      # 1 for single-turn
    expected: ExpectedBehaviour | None    # None when labels are hidden
    tags: list[str]                       # category tags if known (dev set always has them)
    source: Literal["dev", "official"]

@dataclass(frozen=True)
class ExpectedBehaviour:                  # every field optional; dev set fills what it can compute
    decision: Decision | None
    reason: str | None
    product_ids: list[str] | None         # exact expected set (search) or single (lookup)
    price_minor: int | None
    policy_section_ids: list[str] | None
    must_mention_absence: bool | None

def load_cases(path: Path, fmt: str) -> list[EvalCase]: ...    # one parser per official format after UNK-11
```
For `official` cases without visible labels, we compute only label-free metrics (groundedness, citation validity, price hallucinations, latency) and rely on the official evaluator for correctness.

| Category | Target n | Gold source |

## 5. Metrics

All computed by `eval/metrics.py` from responses plus auditor findings. Where expected labels are absent the metric is reported as "n/a", never imputed.

| Metric | Definition |
|---|---|
| **Unsupported claim rate** | Claims with ≥1 auditor finding (§7) ÷ total claims |
| **Groundedness** | 1 − (responses with ≥1 unsupported claim ÷ responses) |
| **Price hallucination count** | Currency amounts in `answer_text`, option labels or suggestions not equal to the price of a product cited in the same sentence. **Severe; release gate = 0.** |
| **Citation validity** | Citations that (a) resolve to an existing product/section/manifest and (b) support their claim (value equality per auditor) ÷ total citations |
| **Decision accuracy** | Confusion matrix over ANSWER/CLARIFY/REFUSE where expected decision is known |
| **Refusal precision / recall** | REFUSE as positive class; also **false-refusal rate** on answerable cases |
| **Clarification precision / recall** | CLARIFY as positive class; also **over-clarification rate** |
| **Product retrieval correctness** | Lookups: returned ID equals gold. Searches: precision = returned ∩ gold ÷ returned (must be 1.0 because hard filters); recall@k = returned ∩ gold ÷ min(k, |gold|) |
| **Field completeness** | For ANSWER lookups, requested fields present and equal to gold values |
| **Helpfulness (PROVISIONAL)** | Proxy: ANSWER cases that supply every requested field and ≥1 product when a search had gold; optional human 0–2 rubric on 20 sampled responses by two reviewers (report inter-rater agreement) |
| **Task success (PROVISIONAL)** | Case succeeds iff decision correct ∧ no auditor findings ∧ retrieval correct (if gold) ∧ fields complete (if answer). |
| **Latency** | Per-query total and stage times; p50/p95/max (§9) |
| **Token usage** | Measured LLM tokens where the runtime exposes them; otherwise labelled estimated/unavailable (§9) |

**Provisional composite (labelled PROVISIONAL, ours, not official):**
`PS = (1/N) · Σ s_i` where `s_i = +1` if task success, `0` if failure, and `−2` if the response contains any price hallucination (the penalty replaces 0/1 for that case). Weights are our own severity choice. The report prints PS only next to the gates below and next to the official evaluator's own score, in separate columns.

**Release gates** (must all hold for the demo build): price hallucinations = 0; template-mode validator trips = 0; groundedness = 1.0 on the dev set; every response valid against its schema.

## 6. Dev-set generation rules (anti-leakage)

- Input: the built SQLite DB and hand-authored lists. **Never** read the official question file or any official expected output.
- A unit test (`T-EVAL-05`) asserts `gen_dev_set.py` does not import or open `data/raw/test_questions*`.
- Each generated case records how its gold was computed (SQL text or "hand-labelled by <member>").

## 7. Independent auditor (`eval/auditor.py`)

Separately implemented; opens SQLite read-only; imports nothing from `app/generation`, `app/decision`, or `app/validation`.

For every `ChatResponse`:
1. Extract every currency amount, product ID and policy marker from `answer_text`, option labels and suggestions (own regexes).
2. For each amount: find the product IDs cited in the same sentence; require equality with that product's DB price.
3. For each cited ID/section: require existence.
4. For claims: re-check type-specific values against the DB (price/stock/rating/category equality; attribute presence; policy quote is a substring of the cited section).
5. For ABSENCE claims: re-run a lexical search with the manifest's constraints and require zero results.
6. Flag any sentence without a citation marker unless it is a known NF template.
7. Output: `findings: list[{case_id, severity, kind, detail}]` with severity `SEVERE` for price mismatches.

## 8. Comparing with hidden expectations without hardcoding

1. Run the official evaluator on the official questions as soon as the bridge works (Day 5), and then **only as a measurement**.
2. Triage failures **by class**, not by question: wrong decision type, wrong constraint parse, missing normalization, wrong boundary semantics, policy coverage mis-threshold, etc. Each fix must be a general rule/config change with a dev-set test reproducing the class.
3. Thresholds are never tuned on official results. If a class appears only in the official set, the team writes **new dev cases of that class** (from the catalogue) and fixes against those.
4. `T-EVAL-06` (anti-hardcoding): a test reads the official question texts (if present locally) and fails if any appears verbatim in `backend/app/**`, `config/**`, or `backend/eval/dev_set/**`. A code-review checklist item forbids question-ID-specific branches.
5. Official outputs are stored with their run metadata so before/after comparisons use the same evaluator version.
6. The change log (`docs/DECISIONS.md`) cites failure classes, never question texts.

## 10. Latency, token and cost measurement

### 10.1 What is recorded per request (`metrics/recorder.py`)

| Metric | Source | Notes |
|---|---|---|
| `total_ms` | wall clock around `Orchestrator.handle` | monotonic clock |
| stage ms | `timer()` blocks: `normalize, extract, merge, retrieve_lexical, retrieve_semantic, filter, decide, evidence, generate_llm, generate_template, validate` | retrieval latency = lexical + semantic + filter |
| model inference latency | `LLMResult.latency_ms`, embedder call timer | separate from retrieval |
| tokens | `LLMResult.input_tokens/output_tokens` with `token_source` | `measured` only if the runtime reports counts; `estimated` if computed with an available tokenizer or `chars/4` (always labelled); `unavailable` otherwise. Embedder token counts: `count_tokens` or `unavailable`. **Never summed across different sources.** |
| memory | `metrics/memory.py` (RSS via `psutil` if installed, else `resource`) | sampled at start-up, after index load, after the benchmark; "n/a" if unavailable |
| external API cost | counter of outbound calls | core design has none → recorded as `0 calls`, and `T-OFF-*` verifies no network use; any Tier 3 optional integration records its own measured usage separately |

### 10.2 Indexing time is separate
`build_index.py` records durations for read, parse, db, fts, embed, policy and total, plus embedding throughput. Reports list "Indexing" and "Query" in separate tables. Query latency never includes indexing or model-loading time; **model load time** is its own line (cold start).

### 10.3 Benchmark script (`scripts/benchmark.py`)

```
python backend/scripts/benchmark.py --suite dev --mode template|llm --warmup 5 --repeat 3 --out data/reports/bench_<ts>.json
```
- Records hardware/OS/Python/library versions and model IDs first (UNK-12).
- Cold-start: time to process startup (container build, model load, index load).
- Warm-up queries are discarded; each query runs `repeat` times; report per-query median and aggregate **p50, p95, p99, max**, stage breakdown, tokens by source, memory snapshots.
- Runs sequentially (single-process, one request at a time) and optionally with N concurrent clients (`--concurrency`) if the team wants to report that.
- Never invents numbers: absent measurement prints `n/a`.
